# Model card: Qwen2.5-Coder-1.5B-Instruct, format fine-tune (checkpoint-250)

A LoRA fine-tune of Qwen2.5-Coder-1.5B-Instruct that answers coding requests with **exactly one fenced Python
block** containing a docstring and type hints, then stops. It is meant to be served as a Q4_K_M GGUF with
llama.cpp on CPU. It is a format adaptation, not a capability upgrade.

## Training

- **Data pipeline:** 50,661 source rows → 50,548 after dedupe → 14,042 prompts with assert-bearing tests →
  6,000 sampled; 4 base-model samples each under a format system prompt → 12,963 passed format checks and
  assert execution in a sandbox → **4,535 SFT examples** (4,383 train / 150 validation; 2 dropped). The system
  prompt is not part of the training input: the model learns the format without being told.
- **Method:** QLoRA (NF4 4-bit base, bf16 compute, gradient checkpointing, `paged_adamw_8bit`), loss on the
  assistant tokens only; the end-of-turn token `<|im_end|>` is trained, padding is masked.
- **LoRA:** r = 16, alpha = 32, dropout 0.05, all 7 linear projections (q, k, v, o, gate, up, down),
  18.46M trainable parameters.
- **Optimisation:** lr 2e-4, cosine schedule, effective batch 16 (micro-batch 2 × 8), seed fixed.
- **Checkpoint used:** step 250 of 273 in epoch 1 (0.91 epochs), the lowest validation loss (0.1299).
  Later checkpoints overfit.
- **Export:** adapter merged into the **bf16** base (training was on NF4 weights, so this is the standard
  QLoRA merge, not an identical model), logits verified on 3 prompts, then GGUF f16 → Q4_K_M.

## Evaluation (HumanEval / HumanEval+, 164 tasks, greedy pass@1, max 768 tokens, seed 42)

| | base bf16 | merged bf16 | Q4_K_M GGUF, model output | **Q4_K_M, as served** |
|---|---|---|---|---|
| HumanEval | 65.2% | 70.1% | 64.0% | **64.6%** |
| HumanEval+ | 59.1% | 66.5% | 61.0% | **61.6%** |
| Format-clean | 5.5% | 100% | 98.8% | **99.4%** |
| Stops on its own | 99.4% | 100% | 100% | **100%** |

As served: the playground adds a missing `typing` import when the model uses a typing name in a type hint without
importing it (a generation-time mitigation, not a change to the model; 1 answer of 164 on HumanEval).

Quantising costs about 6 points against merged bf16 (not significant at n=164; p = 0.12 / 0.18) and leaves
the model level with the original base. Differences against the base are within noise (±7 points); do not read
them as a correctness gain. Details, paired tests, examples and the contamination check:
[eval_report.md](eval_report.md).

## CPU smoke test (llama.cpp b11856, 12 threads)

Prompt "Write a Python function that returns the nth Fibonacci number.": one fenced block with typed
signature, Google-style docstring and an iterative implementation, then end-of-text. 19 tokens/s generation,
71 tokens/s prompt processing, 32 s cold load.

## Limitations

- One benchmark family, one greedy sample per task. No MBPP run. The format checks are the project's own.
- Some topical overlap with classic problems (Roman numerals, Heron's formula, Fibonacci) between training
  and the benchmarks; no copied problems or solutions found. MBPP train/961 has paraphrased training examples,
  so avoid MBPP for evaluation without decontaminating.
- Trained for single-turn requests; behaviour in multi-turn chat or when the user asks for prose is untested.
  It will always answer with one code block.
- The model is 1.5B: expect the usual small-model failure modes (subtle logic errors, wrong edge cases). Measured
  (eval_report.md, "Failure analysis"): most failures are spec reading, dropping a stated rule or solving a nearby
  problem, and most of those are inherited from the base model. It sometimes assigns into a tuple (3 of 40 probe tasks,
  the same rate as the base model) and sometimes uses a typing name in a hint without importing it (1 of 164 on
  HumanEval, 5 of 40 on the probe); the playground adds such imports after generation and marks them.
- Serving needs an OpenMP runtime (`libgomp`) for the llama.cpp CPU build; the container must install it.
